# CallCatch — build contracts (read before writing code)

This file is the integration contract between the parallel build modules. Every module owns a disjoint set of
paths (see `docs/PRODUCT_SPEC.md` for the product and `build_modules` in the build prompt for ownership).
**Never edit a file outside your module's scope.** If you need something changed in a shared file, put it in the
`requests_for_integrator` field of your structured return and code against the contract as written here.

## Stack facts (verify in `node_modules/next/dist/docs/` when unsure)

- **Next.js 16.3 (App Router, Turbopack), React 19, TypeScript strict, Tailwind v4, ESLint 9 flat config.**
- `middleware.ts` is **deprecated** → the file is `proxy.ts` at the project root, exporting `proxy(request: NextRequest)`
  and `config = { matcher: [...] }`.
- Dynamic APIs are async: `const { id } = await params;` `const store = await cookies();` `await headers()`.
- Typed helpers are global (generated by `next typegen`): `PageProps<'/route'>`, `LayoutProps<'/route'>`,
  `RouteContext<'/api/x/[id]'>`. Do not import them.
- `after(() => ...)` from `next/server` schedules work after the response is sent (use it so Twilio webhooks
  return TwiML in < 1s while AI turns run afterwards). Set `export const maxDuration = 60;` on such routes.
- Route Handlers: `export async function POST(request: NextRequest) { ... return Response.json(...) }`.
- Server Functions: files/functions with `"use server"`; call from Client Components or `<form action>`.
- Client Components need `"use client"` at the top. Server Components are the default; keep secrets server-side.
- Tailwind v4: no `tailwind.config.js`; tokens live in `app/globals.css` under `@theme`. Brand tokens available:
  `brand-50…950` (navy), `accent-50…900` (orange), `success-500`, `warning-500`, `danger-500`, `background`, `foreground`.
- Icons: `lucide-react` is installed. No other UI library — plain Tailwind.
- Validation: `zod` v4 (`import { z } from "zod"`).
- Lint: `npm run lint` (`eslint .`). Typecheck: `npm run typecheck` (`next typegen && tsc --noEmit`).
  Other modules are being written concurrently — judge typecheck results by errors in YOUR files only.

## Database conventions (module a defines; everyone follows)

- Table and column names exactly as `docs/PRODUCT_SPEC.md` §4.1. Enums are `text` + CHECK constraints.
- Every account-scoped table has `account_id uuid not null references accounts(id) on delete cascade`.
- RLS: members of `account_members` can select/insert/update rows of their account; service role bypasses.
- Timestamps: `created_at timestamptz default now()`, `updated_at` maintained by trigger.
- `numbers.purpose`: `customer` (a subscriber's line), `notification` (our alerts number), `demo` (public demo line).
- Message direction/author: `direction in ('in','out')`, `author in ('ai','owner','contact','system')`.

## Cross-module runtime contracts

- **Verification → billing**: when `numbers.verification_status` becomes `verified`, module c sets `sms_enabled=true`,
  inserts a `verification_events` row, tracks `verified`, then calls `onVerified(accountId)`.
- **Weekly report**: module c's `/api/cron/weekly-report` runs hourly; for each live account whose local time is
  Monday 07:00–07:59 and with no `weekly_reports` row for this week, it calls `buildWeeklyStats` +
  `renderWeeklyEmail`, sends via `sendEmail`, inserts `weekly_reports`.
- **Lead intake → AI**: module c exposes `lib/leads/intake.ts` `createLeadAndEngage(accountId, input)` used by
  the Resend/webhook/Meta routes (all module c).
- **Alerts**: owner alerts always go from `TWILIO_NOTIFICATION_NUMBER` (our verified number) to
  `accounts.alert_phone`; customer-facing texts go from the account's own `numbers` row (only when `sms_enabled`).
- **Onboarding → core**: module b writes `accounts`, `numbers` (via provisioning route), `lead_sources`; module c
  reads them. Number webhooks set by module b must be exactly:
  voice `${APP_URL}/api/twilio/voice/inbound`, voice status `${APP_URL}/api/twilio/voice/status`,
  sms `${APP_URL}/api/twilio/sms/inbound`.
- **Billing → accounts**: module d's Stripe webhook is the only writer of `subscriptions` and `accounts.plan`;
  it sets `accounts.status='paused'` on pause and `'cancelled'` on cancel; module c pauses AI when status ≠ live/pending_verification.
- **Meta CAPI**: modules b/c/d call `sendCapiEvent` from server code with a stable `eventId` (uuid) that the
  browser Pixel also fires (module f provides `components/marketing/MetaPixel.tsx` + `lib/meta/pixel.ts` client helper
  `trackPixel(eventName, params, eventId)`).

## Claude API rules (module c; see the `claude-api` skill — load it with the Skill tool before writing AI code)

- `import Anthropic from "@anthropic-ai/sdk"`; model ids only from `env.models()`.
- Chat/qualification turns: `thinking: { type: "adaptive" }`, `output_config: { effort: "low" }`, tools with `strict: true`,
  system prompt as a content block array with `cache_control: { type: "ephemeral" }` on the stable business-profile block.
- Extraction/classification with the fast model via structured output (`output_config.format`) or a strict tool.
- Always check `stop_reason` (`refusal` → send the safe template, never crash). Parse tool inputs with `JSON.parse`-safe access.
- Log `usage.input_tokens/output_tokens/cache_read_input_tokens` into `messages.tokens_in/tokens_out/cost_usd`.

## Security rules (all modules)

- Every external webhook verifies its signature (Twilio, Stripe, Resend/Svix, Meta) or a secret (cron, internal, per-account webhook) with `safeEqual`.
- `createAdminSupabase()` only in Route Handlers / Server Functions / crons; never in Client Components.
- Never log secrets, full card data or message bodies with PII at info level.
- Rate-limit code-sending endpoints (alert-phone verification): max 5 sends / 10 min per account (in-memory + DB timestamp is fine).

## Additional cross-module contracts (added by the integrator)

- **Accounts are created by a DB trigger at signup** (module a): `on auth.users insert` → `accounts` row with
  `status='onboarding'`, `owner_user_id`, unique `referral_code`, plus `account_members(role='owner')`. Module b's
  wizard UPDATEs that row; it never inserts accounts. The `(app)` layout (module e) redirects users whose
  `accounts.status === 'onboarding'` to `/onboarding` (except `/onboarding` and `/billing/**`); `proxy.ts`
  (module b) only refreshes the Supabase session and redirects signed-out users away from app routes.
- **Signup → checkout → onboarding order**: `/signup?plan=starter|pro&interval=month|year&path=trial|paynow`
  (module b) → after auth, redirect to `/billing/checkout?plan=…&interval=…&path=…` (module d page that creates the
  Stripe Checkout Session server-side and redirects to Stripe) → Stripe `success_url` = `/onboarding?checkout=success`,
  `cancel_url` = `/billing/checkout?canceled=1`. Trial/pay-now rules: spec §2.
- **Module c exposes** `@/lib/telephony/outbound`:
  `sendCustomerMessage({ accountId, conversationId, body, author: 'owner'|'ai'|'system' })`
  → `Promise<{ ok: boolean; messageId?: string; reason?: string }>` (enforces opt-out, sms_enabled, quiet hours
  by queueing, inserts the `messages` row, sends via the account's number), `pauseAi(conversationId, userId)`,
  `resumeAi(conversationId)`. Module e's inbox Server Functions call these.
- **Module d exposes** `@/lib/billing/usage`: `reportOverageForPeriod(accountId, period /* YYYY-MM-01 */)` → reports
  metered overage to Stripe and sets `usage_monthly.overage_reported`. Module c's nightly `usage-rollup` cron
  computes `usage_monthly` rows then calls it for the previous period on the 1st of the month.
- **Module d exposes** `@/lib/billing/stripe`: `stripe()` client singleton (server-only).
- **Public env var** `NEXT_PUBLIC_DEMO_NUMBER` (E.164) is used by module f for the demo line CTA.
- **Module f may also own** `app/opengraph-image.tsx` and `app/icon.tsx` (generated OG image + favicon via `next/og`).
